> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**

## 프로젝트 우선 조항

이 파일은 프로젝트 기본값(fallback)이다.  
프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있으면 **그 규칙을 우선** 적용하고 이 파일을 무시하라.

---

## 적용 기준

**TDD 필수 적용:**
- 비즈니스 로직 (계산, 변환, 집계, 상태 전이)
- API 엔드포인트 / 서버 핸들러
- 유틸리티 함수
- 버그 수정 — 재현 테스트를 먼저 작성하고 수정

**TDD 불필요:**
- 타입 정의 (`*.ts` 인터페이스/타입만)
- 설정 파일 (vite.config, eslint.config 등)
- 순수 UI 렌더링 (스타일, 레이아웃)
- SQL 마이그레이션 / 스키마 파일

## RED → GREEN → REFACTOR

### RED
- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 번에 테스트하지 마라.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 확인**하라.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류나 import 실패로 인한 실패는 RED가 아니다.

### GREEN
- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI** — 지금 테스트가 요구하지 않는 코드는 작성하지 마라.
- 신규 테스트와 **기존 테스트 모두 통과**를 확인한다.

### REFACTOR
- 중복 제거, 이름 개선, 헬퍼 추출만 허용한다.
- **GREEN 상태를 유지**하며 진행한다. 리팩터 도중 테스트가 깨지면 즉시 되돌린다.
- 새로운 동작을 이 단계에서 추가하지 마라.

### 반복
다음 동작에 대한 RED로 돌아간다.

## 삭제 강제 규칙

테스트 전에 프로덕션 코드를 먼저 작성했다면 **삭제하고 RED부터 재시작**한다.  
"참고용"으로 남기는 것도 금지다. 코드가 존재하면 테스트 작성에 영향을 준다.

## 변명 차단

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드가 가장 자주 깨진다. 단순함은 테스트 작성 비용이 낮다는 뜻이다. |
| "나중에 테스트를 추가하겠다" | 나중은 오지 않는다. 코드가 존재하면 테스트 작성 동기가 사라진다. |
| "시간이 없다" | TDD 없이 작성한 코드의 디버깅 시간이 더 길다. |
| "이미 작성한 코드를 삭제하면 낭비다" | 잘못된 순서로 작성된 코드를 유지하는 것이 낭비다. |
| "프로토타입이라 괜찮다" | 프로토타입은 버려진다. 살아남으면 프로덕션이 된다. |
